## 1. 项目定位与总体目标

Roadbike Atlas 定位为以公路自行车为核心的高精度三维零部件知识与交互展示平台。

项目同时追求三项能力：

1. **高保真整车展示：** 真实几何比例、可信材料质感、产品级视觉表现。
2. **精细化零件拆解：** 支持从整车、系统总成到独立零件的逐级选择、隔离、拆解与装配。
3. **结构知识与机械演示：** 将三维模型与工作原理、规格、安装方法、故障排查和机械运动关联。

这三项能力具有同等战略重要性，但实施必须循序渐进。不以短期视觉效果为由破坏零件结构，也不以机械精度为由忽略网页性能和用户体验。

### 1.1 基本原则

- 保留现有 React、TypeScript、React Three Fiber（R3F）、Three.js 技术栈。
- 优先改进已有模块，不重复建设功能相同的新系统。
- 程序化建模与 GLB 模型允许长期共存。
- 每一类零件必须有稳定的知识分类 ID，每一个可拆卸实体必须有独立实例 ID。
- 真实车型的参数必须具备来源，不能以视觉合理代替几何准确。
- 所有修改必须可测试、可审查、可回退。
- 两人平等开发、交叉审查，不设置永久的技术上下级。

## 3. 技术架构与模块边界

现有项目继续采用纯前端架构，暂不引入后端、数据库或复杂状态管理框架。

系统划分为五层：

| 层次 | 职责 | 当前主要目录 |
| --- | --- | --- |
| 内容领域层 | 零件知识、分类、装配教程 | `content/` |
| 几何与资产层 | 程序化网格、GLB、模型规格 | `src/three/models/` |
| 装配与运动层 | 实例、锚点、拆解、运动约束 | `src/three/` |
| 渲染与交互层 | 相机、材质、灯光、选择、性能 | `src/three/` |
| 页面展示层 | 首页、探索页、零件详情、指南 | `src/pages/` |

### 3.1 数据依赖方向

- 内容层不依赖 Three.js。
- 几何层不直接依赖页面 UI。
- 装配层可以引用零件实例与几何资产，但不应该把 DOM 页面逻辑写入模型生成器。
- 渲染层负责展示与选择，不承担知识数据的定义。
- 页面通过稳定接口调用三维系统，避免直接修改底层网格坐标或材质。

### 3.2 现有模块的演进策略

| 模块 | 演进方式 |
| --- | --- |
| `BikeAssembly.tsx` | 保留，逐步支持实例化装配 |
| `modelRegistry.tsx` | 保留，扩展程序化与 GLB 两类资源 |
| `interaction.tsx` | 保留现有行为，逐步拆分选择、拆解、装配及运动控制 |
| `bikeConfig.ts` | 保留为当前概念车几何配置，未来支持不同车型配置 |
| `PartPreview.tsx` | 保留单件预览，后续统一局部空间和自动取景 |
| `content/schema.ts` | 保持知识数据模型稳定，不与具体三维资产耦合 |

不要求一次性完成迁移，允许新旧接口通过适配器并存。

## 4. 统一零件、装配和模型资产契约

这是 B1 最重要的技术规范。

### 4.1 区分三种身份

**Catalog ID：零件知识分类**

对应现有 27 类零件，例如 `tire`、`hub`、`shifter`，继续用于知识详情、搜索、术语、安装教程。

**Instance ID：场景中的物理实体**

例如：

- `wheel.front.tire`
- `wheel.rear.tire`
- `wheel.front.hub`
- `wheel.rear.hub`
- `cockpit.shifter.left`
- `cockpit.shifter.right`

实例 ID 必须唯一且稳定，不以数组下标生成。

**Asset ID：模型资源**

例如：

- `tire.700x28c.v1`
- `hub.front.generic.v1`
- `shifter.r7100.right.v1`

同一个模型资产允许被多个零件实例复用。**这三种身份不能混用。**

### 4.2 推荐的基础数据接口

```typescript
type Vec3 = [number, number, number];

type AssetSource =
  | {
      kind: 'procedural';
      generatorId: string;
    }
  | {
      kind: 'gltf';
      uri: string;
      nodeName?: string;
    };

interface PartInstance {
  instanceId: string;
  catalogId: string;
  assetId: string;

  parentInstanceId?: string;
  mountAnchorId: string;

  selectable: boolean;
  removable: boolean;
}

interface PartAsset {
  assetId: string;
  source: AssetSource;
}

interface ExplodeRule {
  instanceId: string;
  direction: Vec3;
  distance: number;
  order: number;
}
```

这是**目标数据契约**，不意味着立即替换现有 TypeScript 接口。

### 4.3 迁移原则

1. 引入新契约和适配器。
2. 选择前后轮作为试点，让它们拥有独立的物理实例 ID。
3. 让现有 `PartGroup`、选择控制器和爆炸控制器支持实例 ID，并保留按 Catalog ID 查询知识数据的能力。
4. 逐步迁移剩余零件。

禁止在一个 PR 内将全部 27 类零件强制迁移，以免回归风险失控。

### 4.4 模型所有权

同一个物理零件只允许一个装配组件负责生成其几何。

例如，手变与刹把可以拥有不同知识条目，但不能在整车中重复生成同一个手柄。

对于需要进一步拆解的组合式零件，应定义子节点和独立运动轴，而不是叠加一个新的完整模型。

## 5. 几何建模与机械装配规范

### 5.1 坐标系统

沿用现有仓库约定：

- `+X`：车头方向。
- `+Y`：竖直向上。
- `+Z`：骑手右侧，即传动侧。
- 单位：米。
- 默认使用右手坐标系。

在本次基线中，保留当前模型的世界坐标定位，不强制立即移动整车原点。

### 5.2 局部坐标和装配基准

新开发的零件应尽可能在本地空间建模，由装配器负责定位。

禁止为同一个尺寸在多个模块中分别编写相互独立的魔法常量。

例如前轮轴心、前碟刹轴线、前花鼓中心应通过装配锚点建立关系。

已经存在的绝对坐标模型可以继续运行，但涉及大规模精修时，应优先改为局部空间模型。

### 5.3 真实车型数据

将当前蓝色 ATLAS 模型定义为概念车配置。

它可以借鉴多款现代气动公路车的设计，但不得未经验证就标注为某一真实量产车的精确复刻。

未来新增真实车型时，尺寸应分为：

- `official`：官方公开规格。
- `measured`：实物测量。
- `estimated`：有依据的估算。

必须同时记录来源、单位和适用车型版本。

### 5.4 零件精度分级

| 级别 | 定义 | 验收目标 |
| --- | --- | --- |
| L0：整车视觉级 | 普通整车视角可准确表达部件体量与外观 | 整车轮廓比例合理 |
| L1：零件展示级 | 可信的轮廓、厚度、连接件和主要材质 | 可独立放大观察 |
| L2：机械拆解级 | 真实装配所需的主要子零件和相对位置 | 可逐级拆装 |
| L3：局部机构精细级 | 轴承、棘轮、弹簧、连杆、紧固件等内部机构 | 可用于机械原理演示 |

并非所有零件都要求同时达到 L3。优先根据用户查看频率、结构复杂程度和教学价值确定精修顺序。

## 6. 渲染、材质和性能规范

### 6.1 基本要求

- 保持 `studio.tsx` 作为统一影棚系统的主要实现位置。
- 保持 `materials.ts` 作为材质预设的主要来源。
- 整车视图与零件独立预览必须具有一致的材质表现。
- 材质参数应符合真实材料的反射性质，不以大幅增加金属度、Bloom 或光照强度代替真实感。

### 6.2 资源与材质管理

- 程序化几何允许共享，但实例的交互状态必须独立。
- 外部导入模型需检查材质实例是否共享。
- 禁止因选择一个零件而意外修改其他零件的颜色或透明度。
- 动态创建的资源必须有清晰的释放责任。
- 重复几何优先复用、实例化，但不能牺牲需要的独立选择能力。
- GLB 及其源文件必须明确许可证或使用授权。

### 6.3 性能基线

以现有 `DESIGN.md` 中的性能记录作为历史参考，不直接将其视为所有开发机器的实测结论。

每次涉及模型复杂度、阴影和后处理的 PR，应在相同设备、相同分辨率、相同摄影机位置下记录：

- FPS 或帧时间。
- Draw Call。
- 三角面数量。
- GPU 资源占用（工具可获得时）。
- 资源加载大小和耗时。

初期原则为：不得发生未经说明的显著性能退化。待建立稳定的自动化性能测试环境后，再设置硬性帧率与资源预算。

### 6.4 视觉基准视角

建议固定五类截图：

1. 整车右侧三分之四视角。
2. 整车标准侧视图。
3. 传动系统近景。
4. 车头与手变近景。
5. 爆炸拆解视图。

所有截图使用固定相机参数、光照、曝光和视口配置。

视觉变更必须提供改造前后对比；GPU 平台差异导致的轻微像素变化不应直接判定为失败。

## 7. 双人开发协作规则

### 7.1 团队组织

采用双人平等协作制度。两人都参与需求设计、编码、测试和审查。

模块负责人仅表示当前周期的主要修改责任，不意味着永久技术所有权。

### 7.2 初始任务划分

| 模块 | 开发者 A（你） | 开发者 B（同事） |
| --- | --- | --- |
| 装配实例与模型接口 | 主开发 | 审查 |
| 零件交互、运动控制 | 主开发 | 审查 |
| 车架、轮组几何 | 主开发 | 协助验证 |
| 传动、操控、刹车模型 | 协助验证 | 主开发 |
| 材质和灯光 | 审查与验收 | 主开发 |
| 内容和页面 | 按 Issue 分配 | 按 Issue 分配 |
| 测试与 CI | 共同负责 | 共同负责 |

这只是初始分工。完成一个里程碑后可以交换模块，以减少关键知识集中在一人身上的风险。

### 7.3 文件修改边界

普通独立模型文件由当前任务负责人主导。

以下文件属于共享契约文件：

- `bikeConfig.ts`
- `BikeAssembly.tsx`
- `modelRegistry.tsx`
- `interaction.tsx`
- `geometryHelpers.tsx`
- `materials.ts`
- `studio.tsx`
- `textures.ts`
- `content/schema.ts`
- `package.json`
- CI 与测试基础设施

对于共享文件：

1. 开工前必须在 Issue 或 PR 中声明修改范围。
2. 同一阶段尽量由一个 PR 主导同一个共享文件的结构性修改。
3. 另一方必须进行代码审查。
4. 公共接口变更先合并，再让依赖它的功能分支继续开发。
5. 不允许为了方便个人开发直接破坏现有契约。

### 7.4 日常任务管理

保留现有 GitHub Flow：

**`Issue → 短分支 → Pull Request → CI → Review → Squash Merge`**

每人原则上最多同时主开发一个任务，避免大量未完成分支。

任务应尽量在 1–3 天内形成可独立审核的 PR。复杂任务先拆解，不以一个巨型 PR 完成全部工作。

**Squash Merge 后清理本地分支：** 主分支同步到已合入提交后再删除已结束的工作分支：

```bash
git switch main
git pull --ff-only
# 确认 PR 已合并、工作分支不再包含要保留的提交后再执行
git branch -D feat/example-task
git fetch --prune
```

Squash Merge 会生成新的提交，因此 Git 可能把原本已经通过 PR 合入的工作分支判为“未合并”。`-D` 是强制删除，**只能在核实 PR 已合并、分支无需保留后使用**；否则可能丢失未合并的本地提交。具体操作以 `CONTRIBUTING.md` 为准。

### 7.5 审查制度

双方互相审查对方的 PR。正常情况下必须具备：

- CI 检查通过。
- 作者完成必要的本地验证。
- 另一位开发者审核通过。
- 共享契约变更已说明影响范围。
- 无未处理的阻断性问题。

如因临时原因需要例外合并，必须记录原因、风险、验证方法及回退措施。

**管理员与自我审查的边界：** 仓库当前 `CONTRIBUTING.md` 记录了管理员可能绕过部分主分支保护规则、作者不能批准自己 PR 的情况。两人团队正式协作后，默认仍执行“另一位开发者审核 + CI 通过”，**不因拥有管理员权限而常态化直接推送 `main` 或跳过审核**。如果仅有一人且确有必要使用 `gh pr merge <PR号> --squash --admin` 等例外操作，应先核实仓库设置允许管理员绕过，再记录原因、CI、变更范围与回退方式。具体保护规则是否强制约束管理员，应由仓库管理员在 GitHub Settings 中核实，不能由文档推断。

### 7.6 协作频率

- 开工前同步当前主分支。
- 影响公共接口的任务先沟通。
- 每周至少进行一次简短的开发同步。
- 每个里程碑完成后交换模块知识，避免出现只有一人看得懂的代码。

## 8. 自动化测试与质量门禁

### 8.1 当前必须保留的 CI

沿用现有 `.github/workflows/ci.yml`：

```bash
npm ci
npm test
npm run build
```

PR 与主分支提交应触发这些检查。

### 8.2 B1 应增加的测试

**模型注册测试：** 验证模型引用合法、实例 ID 唯一、Catalog ID 有对应内容，防止注册遗漏。

**几何约束测试：** 验证前后轮轴距、五通下沉、链条节距、碟刹尺寸等基础不变量。

**装配结构测试：** 验证父子关系无环、安装锚点存在、拆解规则合法。

**交互状态测试：** 验证零件选择、隐藏、隔离、爆炸和复位行为不互相破坏。

**渲染冒烟测试：** 逐步引入浏览器端的 WebGL 加载与交互检查，不能依赖 Node 环境中的内容测试代替真实浏览器渲染。

### 8.3 PR 完成定义

一个 PR 只有同时满足以下条件，才视为完成：

- 达到 Issue 所定义的目标。
- 编译和适用的测试通过。
- 不破坏现有主要交互能力。
- 提供必要截图、尺寸检查或性能记录。
- 处理审核意见。
- 合并到 `main` 并确认 CI 成功。

对于不涉及画面的纯文档或数据修改，不强制要求渲染截图。

## 9. GitHub 管理与规范文件职责

### 9.1 不再重复创建现有规范

当前 `CONTRIBUTING.md` 已经规定分支命名、协作流程、冲突解决和基础模块分工。

该文件继续负责日常协作规则。本规范主要负责架构边界、数据契约、模型质量与长期演进。

### 9.2 文档职责

| 文档 | 唯一主要职责 |
| --- | --- |
| `README.md` | 项目介绍、运行及部署 |
| `CONTRIBUTING.md` | 双人 GitHub 工作流程 |
| `DESIGN.md` | 视觉设计与渲染品质 |
| `docs/ARCHITECTURE_BASELINE.md` | 技术架构、契约与基线 |
| `docs/adr/`（按需） | 重要架构决策和修改理由 |

当多个文档存在冲突时，应以针对该问题的专门规范为准，并在同一个 PR 中修正其他文档，避免形成长期不一致。

### 9.3 CODEOWNERS

当前共享文件的 CODEOWNERS 主要配置为 `@Zeno-cc`。

第二位开发者加入仓库后，应根据双方实际 GitHub 用户名更新审查人员配置，并检查分支保护是否真正启用了所需的审批要求。

不能仅凭 `CONTRIBUTING.md` 中的描述推断 GitHub 已经强制执行每条规则。

现有协作文档新增了仓库 owner 的保护规则绕过情况与 `--admin` 合并提示。这属于**已有实践记录**，不是项目对绕过代码审查的默认授权。加入第二位同事后，应优先核实双方的评审权限、required reviews、required status checks，以及管理员 bypass 设置。

### 9.4 基线标签

正式合入本规范并完成一次基准复核后，为**当前 B0 基准提交 `7038bcf3`** 创建 Git Tag（建议 `baseline-v0.1.0`）。该标签所指向的提交与后续纳入规范文档的提交可以不同。

标签一经发布不得移动。需要调整技术基线时，应发布新的基线版本，而不是覆盖旧标签。

## 10. 技术决策与架构变更管理

将技术决策分为三个等级。

### 10.1 普通改动

局部几何细节、文案、独立 UI 等不影响公共接口的变更，由当前负责人开发并通过普通 PR 审查。

### 10.2 共享契约变更

例如修改坐标系统、模型注册接口、装配数据模型、材质公共约定。必须事先说明兼容性和迁移方案，并获得另一方审核。

### 10.3 重大架构决策

例如引入后端、全面更换渲染引擎、取消程序化建模、改变内容数据结构等，必须形成简短 ADR，说明：

- 当前问题是什么。
- 考虑过哪些方案。
- 为什么选择该方案。
- 对现有模块和协作的影响。
- 如何迁移、验证和回退。

两人意见不一致时，不应直接在主分支上试错。可以使用隔离的实验分支做小型 PoC，以测试结果决定。

- [ ] 保留原有六大系统和 27 类零件的知识数据。

- [ ] 新增几何、注册、装配相关的核心自动化测试。
- [ ] 具备固定视角的渲染对比材料和可重复的性能测量流程。
- [ ] 双方能够独立开发模块，通过 PR 正常合并并回退。
- [ ] 技术规范、源码、测试及 GitHub 协作流程保持一致。

达到 B1 后，再进入多车型支持、完整机械运动、内部机构精细化和更高级渲染的后续阶段。

## 13. 冻结结论

**本规范明确冻结的是工程契约，而不是视觉创作空间。**

不应频繁修改的内容包括：坐标系统、稳定 ID 规则、装配关系接口、内容模型兼容性、构建工具链和质量门禁。

可以持续优化的内容包括：几何精度、零件资产、材质表现、光照、动效、页面设计、性能和知识资料。

Roadbike Atlas 长期采用 **“稳定内核 + 可替换模型资产 + 可扩展交互能力”** 的架构。

所有架构升级采用渐进式迁移，不以推倒现有原型作为默认方案。

**版本约定：** B0 为现有可运行工程快照；B1 为下一阶段架构目标。后续正式版本以实际通过评审、CI 与验收的提交为准。
